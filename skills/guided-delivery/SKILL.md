# 引导式交付

先读取 `mvp-delivery` 和 `delivery-report` 的流程。`guided-delivery` 始终启用 `delivery-report`：范围清晰后在当前对话建立交付记录，并在关键决定、实质改动、验证结果和风险发现后更新。开始时不要写代码、创建依赖或运行变更命令；不执行 commit、push、PR 或远端写操作。

## 一问一答地收敛

1. 从题目和现有代码中直接发现的信息不要再问。
2. 每次只问一个会改变范围、数据/API、权限、失败语义、验收或时间计划的关键问题。
3. 每个问题都给出推荐答案和简短理由；等用户回答后，再问下一题。
4. 每次回答后更新“共识记录”，并同步交付记录中的已确认决定与范围。

共识记录必须包含：

- 目标用户路径；
- 最小范围和非目标；
- API、数据模型和状态语义；
- 关键边界与失败语义；
- 验收测试；
- 方案取舍与时间盒计划。

六项完整后，展示共识记录，并明确要求用户输入“确认实施”或语义等价的许可。用户没有确认时，只能继续澄清、调整记录或解释方案；不得开始实施。

## 确认后的阶段路由

1. 读取并遵循 `feature-slice`，列出受影响文件、最小垂直切片和测试方案后实施，并记录实际改动。
2. 验证主链路、相关异常状态和系统边界，并记录命令或人工检查的结果。
3. 读取并遵循 `engineering-review`，只报告有证据的高价值问题，并记录阻塞项与其处置结果。
4. 测试失败、运行报错或行为不符时，读取并遵循 `debug-loop`；先复现和收集证据，不得猜测修复，并记录根因和回归结果。

正确性、安全或验收阻塞问题必须说明“证据 → 影响 → 最小修复”，等待用户确认后才修复并回归验证。非阻塞优化只记录为后续建议，不中断交付。

## 交付总结

结束时按任务类型输出 `delivery-report` 的中文交付报告，涵盖交付内容、验证结果、已确认的取舍、剩余风险和下一步。默认仅在对话输出；只有用户明确要求且项目已有合适文档位置时才写入文件。AI 只提供候选方案和执行辅助；关键决策、代码审查和交付结论始终由用户负责。
