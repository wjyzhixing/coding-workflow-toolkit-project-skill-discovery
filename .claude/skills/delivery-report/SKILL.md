# 交付记录与报告

在当前对话中维护一份简短的交付记录，并只用已验证的事实生成最终报告。项目根目录每个任务最多只能有一个任务/报告目录：先检查并复用已有的交付、评估或结果目录，不得因需求简称、前缀（如“xxxxx-”）或阶段名称不同而创建第二个目录。只有确认不存在已有目录时，才使用确认的完整需求名创建一个目录并写入 `交付报告.md`；若已有结果且用户未要求补充报告，不创建报告目录。最终回复给出摘要和现有报告文件链接；需求名不明确时先向用户确认。

## 硬性边界

- 不执行 `git commit`、`git push`、创建 PR 或任何远端写操作。
- 不把假设、计划或未验证的推测写成已完成事实。
- 不记录普通命令、重复尝试或内部推理，只记录会影响交付判断的事件。
- 发现阻塞验收的问题时，先记录“证据 → 影响 → 最小修复”，并等待用户确认后再修改。

## 维护交付记录

任务范围清晰后立即建立记录。每次用户确认关键决定、完成实质改动、得到验证结果或发现风险时更新一次。

| 字段 | 内容 |
| --- | --- |
| 任务类型 | 需求、功能、问题/缺陷或笔试题 |
| 目标 | 用户可感知的结果和主路径 |
| 范围 | 已确认的内容与明确非目标 |
| 关键决策 | 重要取舍及其原因 |
| 实际改动 | 文件、接口、行为或数据流变化 |
| 验证证据 | 测试、构建、人工检查及其结果 |
| 风险与下一步 | 已知缺口、假设和建议 |

目录名使用确认的完整任务名，并仅替换路径分隔符等不安全字符；写入前必须检查项目根目录，复用唯一已有任务目录。每个任务只维护一个目录及其对应的 `交付报告.md`，禁止创建简称目录、前缀目录、阶段目录或额外报告层级。

## 生成最终报告

先按任务的主要意图选择一种模板，开头直接给出交付结果，并保持简洁。

### 需求报告

1. 背景与目标
2. 已确认范围与非目标
3. 用户路径，以及必要的数据、状态或 API 契约
4. 验收标准与验证结果
5. 已确认取舍、剩余风险与下一步

### 功能报告

1. 已交付的用户价值
2. 行为变化和受影响文件或接口
3. 明确未做的内容
4. 验证证据
5. 剩余风险与后续建议

### 问题/缺陷报告

1. 预期行为与实际行为
2. 复现证据与根因
3. 最小修复及其边界
4. 回归覆盖与验证结果
5. 剩余风险、监控或后续项

### 笔试题报告

1. 假设与时间盒范围
2. 方案或实现，以及核心取舍
3. 如何处理主要性能、正确性或体验风险
4. 验收检查或可演示证据
5. 若继续投入的优先改进项

## 输出前检查

- 区分已确认事实、假设与剩余风险。
- 只列出实际发生的改动和已运行的验证。
- 说明验证失败或未覆盖项，不暗示全部通过。
- 不包含 commit、push、PR 或远端操作指令。
