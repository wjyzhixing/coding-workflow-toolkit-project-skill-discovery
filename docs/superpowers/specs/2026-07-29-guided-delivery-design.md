# Guided Delivery 总控 Skill 设计

## 目标

提供唯一入口 `$guided-delivery`：用户给出初始问题后，它以一问一答的方式完成设计共识，只有得到明确“确认实施”后才进入代码实现；实现、验证、审查和故障定位按需复用现有的四个通用 skills。

## 路由与职责

`guided-delivery` 是状态机与对话主持人，不是黑盒自动化器。它会按阶段读取并遵循下列技能：

| 阶段 | 子 skill | 总控职责 |
| --- | --- | --- |
| 澄清与取舍 | `mvp-delivery` | 每次只问一个影响设计的问题，给出推荐答案和理由 |
| 已有代码中的实现 | `feature-slice` | 形成文件范围、最小垂直切片和测试计划 |
| 完成后审查 | `engineering-review` | 仅报告有证据的高价值风险 |
| 失败或异常 | `debug-loop` | 先复现和收集证据，再提出最小修复 |

## 状态机与确认边界

```text
初始题目
  → 一问一答澄清
  → 共识记录
  → 等待“确认实施”
  → 最小功能切片
  → 验证
  → 工程审查
  → 交付总结
```

开始实施前的共识记录必须包含：目标用户路径、最小范围和非目标、API/数据模型/状态语义、关键边界与失败语义、验收测试、方案取舍与时间盒计划。

用户只有明确说出“确认实施”或语义等价的许可后，才允许写入应用代码、创建依赖或运行变更命令。用户可在任一阶段要求修改共识记录；此时必须回到相应的澄清步骤。

## 收尾规则

- 正确性、安全或验收阻塞问题：给出证据、影响、最小修复，等待确认后修复并回归验证。
- 非阻塞优化：记录为后续建议，不中断交付。
- 测试失败、运行报错或行为不符：切换到 `debug-loop`；不得猜测修复。
